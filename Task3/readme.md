### <a name="_qmphm5d6rvi3"></a>**Решение**

В качестве MVP решения предлагается выделить новую систему управления депозитами и кредитами.

В последствии всю логику по ставкам, кредитам, депозитам, общим балансам предлагается размещать в рамках данной системы.

Для решения задачи подачи заявок открытия депозитов через сайт/интернет-банк разработать новый микросервис "Управления депозитов".

Взаимодействие между сервисами/системами в комании предлагается организовать c использованием брокера Kafka.

Новые сущности и процесс размещать в отдельных от существующих СУБД. В качестве СУБД предлагается выбрать Postgres.

Интерфейсы пользователя реализуются в соответствующих системах сайта и интернет-банка - их бэкенд компоненты проксируют запросы пользователя в сервис открытия депозитов.

[Диаграмма контекста](c4_context.puml)

[Диаграмма контейнеров](c4_container.puml)

Нефункциональные требования в MVP не в полной мере соответствуют всем заявленным функциональным требованиям ввиду
обеспечения более высокой скорости разработки и достижения результата.

Например: обеспечение катастрофоустойчивости для новых сервисов является сложной задачи, требующей огромной экспертизы и
больших ресурсных вложений, особенно при необходимости поддержки режима active-active. Потеря данных о заявках на
депозиты не является критической для бизнеса информацией в случае если в 1 ЦОД "прилетит ракета". Требуется согласовать
данную позицию с бизнесом и обосновать отсутствие необходимости обеспечения катастрофоустойчивости на данном этапе.

Использование Postgres вместо MS SQL и Oracle требуется обосновать и согласовать с бизнесом:
* соответствие импортозамещение ввиду прекращения официальной поддержки на территории РФ;
* наличие OpenSource варианта использования СУБД;
* наличие официально вендора Postgres Pro в случае необходимости сопровождения нагруженной и объёмной СУБД.

Использование Java + Spring Boot:
* большое количество специалистов на рынке, популярные технологии - высокие шансы набора команды с рынка/подключение аутсорс специалистов;
* OpenSource;
* наличие опыта у специалистов смежных команд - возможность шэринга экспертизы;
* унификация стека внутри компании на перспективу - гибкость в перемещении людей между командами, возможность запуска централизованных обучений;

Обеспечение высокой доступности и скорости обработки обеспечено:
* новая функциональность не должна тормозить с целью привлечения клиентов на онлайн ресурсы, а не их оттока из-за "тормозов";
* горизонтальное масштабирование позволит удерживать возможность обеспечивать "большой наплыв" пользователей в случае успеха разработанной функциональности; 
* шифрование позволит избежать утечки персональных данных пользователей - что является непозволительным для банка, как репутационно, так и юридически/финансово;
### <a name="_bjrr7veeh80c"></a>**Альтернативы**

#### Разработка логики на существующих компонентах - сайт/банк

Плюсы: команды знакомы со стеком, упрощение разработки и доставки;
Минусы: БД перегружены, горизонтально масштабироваться возможность отсутствует - есть риск попасть в безвыходную ситуацию из-за повышения нагрузки после релиза.

#### Синхронные (HTTP) интеграции между системами вместо асинхронных

Плюсы: упрощение разработки
Минусы: сложность интеграции, отсутствие контроля пропускной способности ИБ

#### Использование проприетарный СУБД вместо OpenSource

Минусы: риски при прекращении поддержки, увеличение расходов на ПО;
Плюсы: известная командам технология


### <a name="_bjrr7veeh80c"></a>**Недостатки, ограничения, риски**

Недостатки и ограничения: смотри в альтернативах.

Риски:
* использование нового для некоторых людей стека технологий - требуется организовать обучения, митапы, подбор обучающих материалов;
* ввиду "подстилания соломы" на будущие трансформации и фичи есть шансы не успеть MVP в срок - наименее критичные модификации и рефакторинг тербуется отложить на конец с целью ускориться;
* сопротивление новому стеку технологий - есть риск утечки кадров - нивелируется популярным стеком - допустимо "подложить солому" запуском набора новых специалистов с рынка.
