### <a name="_qmphm5d6rvi3"></a>**Решение**

Для решения задачи подачи заявок открытия депозитов через сайт/интернет-банк разработать в АБС новый "Сервис управления
депозитами".

#### <a name="_qmphm5d6rvi3"></a>**Описание потоков данных**

Процесс актуализации депозитных ставок в системе:

1. Ежедневно менеджер бэк-офиса обновляет ставки через интерфейс АБС
2. "АБС" по HTTP проксирует запрос в "Сервис управления депозитами"
3. "Сервис управления депозитами" сохраняет ставки в БД Postgres

Процесс подачи заявки открытия депозита через "Сайт":
1. "Сайт" получает запрос от пользователя
2. "Сайт" по HTTP проксирует заявку пользователя в "Сервис управления депозитами"
3. "Сервис управления депозитами" сохраняет заявку, генерирует код СМС, сохраняет в БД Postgres и направляет в "СМС-щлюз" смс с подтверждением кода
4. Пользователь получает СМС и отправляет его на "Сайт"
5. "Сайт" проксирует запрос в "Сервис управления депозитами"
6. "Сервис управления депозитами" принимает код и по kafka направляет заявку в кол-центр на обработку заявки
7. Сервисы кол-центра вычитывают заявку из Kafka 
8. Менеджер кол-центра берет заявку в работу, связывается с клиентом

Процесс подачи заявки открытия депозита через "Интернет-банк":
1. "Интернет-банк" получает заявку пользователя на открытие депозита
2. "Интернет-банк" по HTTP проксирует заявку пользователя в "Сервис управления депозитами"
3. "Сервис управления депозитами" перенаправляет заявку в kafka
4. "АБС" вычитывает заявку из kafka и сохраняет в БД Oracle
5. Менеджер депозитов открывает заявку в интерфейсе "АБС", обрабатывает заявку и направляет информацию со ставками клиенту в СМС
6. "АБС" обновляет статус заявки в БД Oracle

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

#### Разработка логики на существующих компонентах - сайт/банк

Плюсы: команды знакомы со стеком, упрощение разработки и доставки;
Минусы: БД перегружены, горизонтально масштабироваться возможность отсутствует - есть риск попасть в безвыходную
ситуацию из-за повышения нагрузки после релиза.

#### Использование проприетарный СУБД вместо OpenSource

Минусы: риски при прекращении поддержки, увеличение расходов на ПО;
Плюсы: известная командам технология

### <a name="_bjrr7veeh80c"></a>**Недостатки, ограничения, риски**

Недостатки, риски и ограничения:
* обработка заявок менеджером происходит в АБС, хотя БД АБС перегружена - в перспективе требуется разработать WEB-интерфейс для менеджера для обработки заявок по депозитам;
* ручная загрузка ставок менеджером депозитов в АБС;
* использование нового для некоторых людей стека технологий - требуется организовать обучения, митапы, подбор обучающих
  материалов;
* ввиду "подстилания соломы" на будущие трансформации (Postgres, микросервисы, новый стек) и фичи есть шансы не успеть MVP в срок - наименее критичные
  модификации и рефакторинг требуется отложить на конец с целью ускориться;
* сопротивление новому стеку технологий - есть риск утечки кадров - нивелируется популярным стеком - допустимо "подложить солому" запуском набора новых специалистов с рынка.
